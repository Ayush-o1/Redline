# Architecture

## Overview

Redline turns an OpenAPI specification into executed, reported-on API tests,
with an LLM in the loop for the parts that benefit from it (scenario design,
test authoring) and deterministic code everywhere trust matters (parsing,
validation, execution, reporting).

```
 OpenAPI spec (YAML/JSON)
        |
        v
 ┌─────────────────┐
 │  openapi/        │  loader.py:    structural validation, clear errors
 │                  │  normalize.py: raw dict -> ApiModel (Endpoint, Parameter, ...)
 └────────┬─────────┘
          v
 ┌─────────────────┐
 │  generation/     │  prompts.py:    endpoint context -> system/user prompt
 │  (per endpoint)  │  provider.py:   LLMProvider (OpenAI | Mock)
 │                  │  generator.py:  raw text -> TestPlan -> list[TestCase]
 └────────┬─────────┘  (Pydantic validates every response; malformed output
          v             raises GenerationError, it never reaches later stages)
 ┌─────────────────┐
 │  validation/     │  validator.py: deterministic checks against ApiModel
 │                  │  (endpoint exists, params known, status plausible, ...)
 │                  │  + dedup by (method, path, category, assertions)
 └────────┬─────────┘
          v
 ┌─────────────────┐
 │  repair/         │  loop.py: one failing case + its error -> the model ->
 │  (bounded)       │  re-validate. Repeats up to --max-retries, never bypasses
 │                  │  validation, every attempt recorded.
 └────────┬─────────┘
          v
 ┌─────────────────┐
 │  execution/      │  harness_test.py: fixed pytest file, turns TestCase JSON
 │                  │  into HTTP requests + assertions (see "Safe execution")
 │                  │  runner.py: subprocess pytest + pytest-json-report
 └────────┬─────────┘
          v
 ┌─────────────────┐
 │  reporting/      │  report.py:   RunReport -> reports/run-<id>.json
 │                  │  markdown.py: -> reports/test-plan.md (human review)
 └──────────────────┘
```

`core/pipeline.py` is the only module that calls all of the above in
sequence; every other module can be understood and tested in isolation.

## Why structured output, not free-form text

The model is never asked to write Python. It is asked to produce JSON that
matches a fixed Pydantic schema (`redline.models.testcase.TestCase`). This
means "did the model produce something usable" is a parsing question with a
yes/no answer, not a judgment call -- `TestCase.model_validate(...)` either
succeeds or raises. Everything downstream operates on model instances, never
on raw text, so there is no place where a stray sentence or markdown fence
from the model can leak into a decision.

The pipeline also splits generation into two LLM calls per endpoint instead
of one:

1. **Plan** (`generate_test_plan`): a short list of scenario descriptions
   ("missing required field 'title' returns 400"). This is the layer a human
   reviewer would look at to sanity-check *coverage* before any code exists.
2. **Test cases** (`generate_test_cases`): the approved scenarios turned into
   the full `TestCase` schema (request, expected status, assertions).

Splitting these matters because it is much easier to eyeball "are these the
right 6 scenarios for this endpoint" as a sentence list than to review 6 full
JSON objects, and it keeps each individual prompt focused on one concern.

## Why LLM output is treated as untrusted

Nothing produced by the model is executed as code, ever. The alternative
architecture -- have the model write pytest source files directly -- was
rejected specifically because it would require either running LLM-authored
Python (arbitrary code execution risk) or building a sandboxing layer to
contain it (real complexity for a two-day project, and still an attack
surface).

Instead:

- The model only ever produces **data**: a JSON object matching the
  `TestCase` schema.
- `redline/execution/harness_test.py` is Redline's own source code. It is
  fixed, reviewed, and never modified or generated by the model. It reads
  validated `TestCase` JSON and turns it into an HTTP request + assertion
  check using `httpx`.
- There is no code path in the entire pipeline where a string that came from
  the model is passed to `eval`, `exec`, a shell, or a template that renders
  to executable Python.

This is also why validation exists as a separate, deterministic stage
(`redline/validation/validator.py`) rather than trusting the model's own
claims: every generated case is checked against the *actual* normalized API
model (`ApiModel`) before it is allowed anywhere near execution -- does the
endpoint exist, is the method defined, are referenced parameters real, is the
expected status remotely plausible, do header/parameter values contain
control characters that could enable request-smuggling. A case that fails
any of these is rejected, not "fixed silently."

## Why tests are executed, not just generated

A test that was never run is a guess. Redline always executes validated
cases with pytest against a real target (the bundled demo app, or any
OpenAPI-described API reachable at `--target-base-url`) and reports actual
pass/fail/error outcomes. This is the difference between "the AI wrote some
JSON that looks like a test" and "the AI wrote a test, and it verifiably
passes or fails against the real system." Execution runs in a subprocess
(not in-process `pytest.main()`) so a hanging or misbehaving target cannot
destabilize the Redline CLI process itself, and so each run gets a clean
plugin/import state.

## The repair loop

When a case fails -- either during validation (structurally invalid) or
during execution (the assertion didn't hold) -- Redline sends the model
exactly one thing back: the failing case, the specific error, the endpoint
context, and the attempt number. It does not resend the whole conversation,
other test cases, or the environment. The model's repaired output goes
through the *same* validation path as any freshly generated case; the repair
loop has no special privilege to bypass checks. Retries are capped by
`--max-retries` (default 2); every attempt, successful or not, is recorded
in the run report.

## CI behavior

`ci.yml` never calls a real LLM. All generation-stage tests use
`redline.generation.provider.MockProvider`, seeded with canned responses
checked into `tests/fixtures/mock_llm_responses/`. This keeps the test suite
free, fast, and deterministic, and means a broken `OPENAI_API_KEY` or an
OpenAI outage can never fail CI. A separate `integration.yml` workflow
(manual trigger only, `workflow_dispatch`) exercises a real API key against
the bundled demo app when someone explicitly wants to validate that path.

## Failure handling summary

| Failure point                          | Handled by                          | Outcome                                   |
|-----------------------------------------|--------------------------------------|--------------------------------------------|
| Spec file missing / malformed YAML/JSON | `openapi/loader.py`                  | `RedlineSpecError` with the exact problem  |
| Spec missing required OpenAPI fields    | `openapi/loader.py`                  | `RedlineSpecError` naming the missing field|
| Model returns non-JSON text             | `generation/generator.py`            | `GenerationError`, endpoint skipped, logged|
| Model JSON doesn't match schema         | `generation/generator.py` (Pydantic) | invalid cases dropped; valid ones kept     |
| Case references a nonexistent endpoint  | `validation/validator.py`            | rejected, eligible for repair              |
| Case passes validation, fails execution | `execution/runner.py` + `repair/`    | repair attempted up to `--max-retries`     |
| pytest itself cannot run                | `execution/runner.py`                | `ExecutionError` with captured stdout/stderr|
